## 🎯 1. PROBLEM STATEMENT

La app Flutter de administración mobile (DiceProjects Admin) presenta problemas de UX/UI y navegación que degradan la usabilidad diaria y generan fricción operativa, sin que exista un problema de lógica de negocio.

- ¿Qué está fallando hoy?
  - Overflows horizontales/verticales en múltiples pantallas.
  - Elementos fuera de “safe area” (ej.: FAB cortado en mobile).
  - Jerarquía visual pobre (cards y listados confusos; demasiado espacio desperdiciado).
  - Textos largos rompen layout (nombres/roles/valores extensos).
  - Renderizado crudo de objetos (ej.: roles como texto sin formato, ilegibles).
  - Dark/light mode inconsistente entre pantallas y componentes.
  - Buscadores visualmente poco integrados y no consistentes.
  - Login con layout “alto”/poco enfocado.
  - Dashboard “se ve mal” (percepción de baja calidad/poco profesional).
  - Botón “atrás” (sistema/back) está mal resuelto: en escenarios no-root cierra la app.
  - Botones de “crear” se perciben “feos”/inconsistentes.
- ¿Quién lo sufre exactamente?
  - Operadores/administradores que usan la app a diario para gestionar usuarios, auditoría y productos.
  - Equipo interno (soporte/QA/dev) por retrabajo y bugs visuales recurrentes.
- ¿Con qué frecuencia ocurre?
  - Alta: ocurre en uso cotidiano (listas, formularios, navegación) y varía por tamaño de pantalla.
- ¿Cuál es el impacto operativo?
  - Lentitud para completar tareas, errores por lectura/interpretación, frustración en navegación.
  - Dificulta la adopción interna/cliente cuando se usa en demos o en campo.
- ¿Cuál es el impacto económico?
  - Costo de soporte y retrabajo (hotfixes visuales), pérdida de eficiencia del equipo.
- ¿Qué pasa si no se resuelve?
  - Deuda UX acumulada, más bugs visuales por cada cambio, menor confianza en el producto.

## 💎 3. VALUE PROPOSITION

Qué cambia concretamente para el usuario (sin cambiar funcionalidad de negocio):

- Beneficio directo (medible)
  - Uso sin overflows/cortes en pantallas objetivo y tamaños de pantalla representativos.
  - Navegación “atrás” correcta: vuelve a la pantalla previa (no cierra la app fuera del root).
- Beneficio indirecto
  - Mayor percepción de calidad ("premium/corporativo"), mejor consistencia visual.
  - Menos incidencias/ajustes ad-hoc por pantalla.
- Diferenciador clave
  - “Calidad móvil” consistente: safe areas + dark/light sólidos + jerarquía clara.
- Alternativa actual vs nueva solución
  - Actual: UI fragmentada por pantalla, componentes no reutilizables, fallas recurrentes.
  - Nueva: sistema de componentes reusable + reglas de layout + navegación estándar.

## 📦 5. FUNCTIONAL SCOPE (MVP)

### Incluye (justificado):
- [ ] Refactor UX/UI (sin cambios de negocio) en pantallas objetivo:
  - Login → problema que resuelve: layout alto, poca claridad, baja “conversión” interna.
  - Parámetros → problema que resuelve: consistencia visual y accesibilidad.
  - Auditoría → problema que resuelve: legibilidad de listados y textos largos.
  - Usuarios → problema que resuelve: listados claros, buscador consistente, cero overflows.
  - Detalle de usuario → problema que resuelve: presentación clara, roles legibles (chips/lista).
  - Productos (empty state) → problema que resuelve: estado vacío consistente y “corporativo”.
- [ ] Dashboard (home/admin) → problema que resuelve: “se ve mal”, jerarquía visual pobre.
- [ ] Corrección de navegación “atrás” → problema que resuelve: cierre inesperado de app.
- [ ] Sistema de componentes reutilizables (solo UI) para reducir inconsistencias:
  - Theme centralizado (dark/light consistente)
  - Cards consistentes
  - Search bar consistente
  - Status chips
  - Empty states
  - App form fields
  - Primary button
  - Theme toggle más compacto
  - Reglas para textos largos (truncado/wrap/ajuste)
- [ ] Safe areas y posicionamiento correcto de FAB (no cortado) en pantallas donde exista.
- [ ] Consistencia de botones “crear” (estilo/jerarquía) sin cambiar acciones.

### Excluye (explícito):
- [ ] Nuevos módulos/pantallas de negocio no existentes
- [ ] BI/analytics nuevos, dashboards analíticos, métricas dentro del producto
- [ ] Cambios de backend, APIs, modelos de datos, reglas de negocio
- [ ] Nuevos flujos funcionales (solo se mejora UI/UX de flujos actuales)
- [ ] Redefinición de permisos/roles/autorización

⚠️ Si algo no está en MVP, NO existe.

## 📜 6. BUSINESS RULES (EXPLÍCITAS)

1. No se modifica la funcionalidad de negocio: mismas acciones, mismos endpoints, mismos permisos, mismo resultado funcional.
2. Criterio de layout: ninguna pantalla objetivo puede producir overflow (horizontal/vertical) en dispositivos y fuentes típicas; los textos largos deben degradar de forma controlada (wrap/truncate) sin romper.
3. Criterio safe area: elementos de acción (incl. FAB) y contenido principal deben respetar safe area y no quedar cortados por notch/gestos/barra del sistema.
4. Criterio dark/light: el modo oscuro/claro debe ser consistente en todas las pantallas objetivo; el contraste debe ser legible y coherente.
5. Regla de navegación “atrás”: el botón/sistema back debe retornar a la pantalla previa cuando haya historial de navegación; solo puede cerrar la app cuando el usuario está en la ruta raíz (home) y el sistema lo determina.
6. Consistencia de componentes: botones, cards, search bar, chips y empty states deben reutilizarse; no se aceptan variantes por pantalla sin justificación.

## 📈 8. KPI & DEFINITION OF VALUE

### KPI de Producto:
- % de pantallas objetivo sin overflows en QA (target: 100%).
- % de componentes reutilizados vs componentes ad-hoc en pantallas objetivo (target: ≥80% de uso de componentes estándar en esas pantallas).
- Tasa de navegación correcta (casos de back que retornan al flujo esperado) en UAT (target: 100% de casos definidos).

### KPI de Negocio:
- Reducción de incidentes/bugs UX/UI reportados post-release (target: -60% en 30 días, vs baseline).
- Reducción del tiempo promedio para completar tareas de admin comunes (target: -20% en tareas seleccionadas).

### Definition of Value:
El producto es exitoso cuando:

- [ ] No hay overflows/cortes en pantallas objetivo bajo casos de UAT.
- [ ] FAB y acciones quedan visibles y accesibles en dispositivos con notch/gestos.
- [ ] Dark/light es consistente y legible.
- [ ] La navegación back funciona como espera el usuario (no cierra la app fuera del root).

## 🧪 11. ASSUMPTIONS & VALIDATION

- Supuesto crítico 1: la mayor parte del dolor proviene de UI/layout y no de lógica de negocio.
  - Cómo se valida: UAT de tareas existentes completadas sin cambios funcionales; comparación de resultados.
  - Qué resultado lo invalida: se detectan cambios requeridos en APIs/reglas para “arreglar” la UX.

- Supuesto crítico 2: la inconsistencia visual se reduce con componentes reutilizables y theme centralizado.
  - Cómo se valida: auditoría de pantallas objetivo y reducción de variantes ad-hoc.
  - Qué resultado lo invalida: cada pantalla requiere excepciones y no converge a un set común.

- Supuesto crítico 3: el problema de back navigation es de flujo/ruteo y se puede corregir sin cambiar negocio.
  - Cómo se valida: casos UAT de back por pantalla; evidencia de navegación correcta.
  - Qué resultado lo invalida: dependencias funcionales que obligan a rediseñar flujos.

⚠️ Si no se valida, es una apuesta.

## ⚖️ 12. PRIORITIZATION RATIONALE

- Se priorizan pantallas de uso frecuente (Login, Usuarios, Detalle, Auditoría) porque concentran fricción diaria.
- Se priorizan safe area/FAB y overflows porque son fallas “bloqueantes” de usabilidad.
- Se prioriza back navigation por ser un error crítico de interacción que rompe expectativa estándar.
- Se prioriza theme/componentes porque habilitan consistencia y reducen costo futuro sin agregar features.
