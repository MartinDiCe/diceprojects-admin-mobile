## 🎯 1. OBJETIVO DEL PLAN

Refactorizar la capa de presentación de la app Flutter mobile `app-diceprojects-admin` para eliminar overflows, corregir navegación back, respetar safe areas y consolidar un set mínimo de componentes UI reutilizables. El resultado debe ser una app con calidad visual consistente y navegación estándar, sin alterar lógica de negocio ni backend.

### Este plan cubre:

- Corrección de navegación back: uso correcto de `push`/`pushReplacement` vs `go()` en go_router.
- Eliminación de overflows (horizontal y vertical) en pantallas objetivo.
- Corrección de safe area y posicionamiento de FAB.
- Auditoría y consolidación de componentes UI existentes (`lib/core/ui/widgets/`).
- Creación o refinamiento de los componentes mínimos faltantes: `AppSearchBar`, `StatusChip`.
- Validación técnica: `flutter analyze` limpio + build debug APK.

### No cubre:

- Cambios en backend, APIs, modelos de datos o reglas de negocio.
- Nuevas pantallas o módulos de negocio no existentes.
- Nuevos flujos funcionales; solo se mejora UI/UX de flujos actuales.
- Redefinición de roles/permisos/autorización.
- Extensión del refactor a pantallas fuera de la lista objetivo (queda en roadmap Fase 1 del producto).

### Restricciones heredadas desde `.product.md`:

- Ninguna pantalla objetivo puede producir overflow en dispositivos y fuentes típicas.
- Textos largos deben degradar de forma controlada (wrap/truncate).
- Modo oscuro/claro debe ser consistente en todas las pantallas objetivo.
- Back navigation: solo puede cerrar la app en ruta raíz; en cualquier otra pantalla debe retornar al paso previo.
- No se aceptan variantes de componentes por pantalla sin justificación explícita.

## 🧱 3. PRINCIPIOS ARQUITECTÓNICOS

- **Clean Architecture pragmática:** la capa de presentación (widget/screen) no conoce la capa de datos; se comunica solo a través de providers Riverpod. Este refactor no debe romper ese límite: solo se toca `presentation/`.
- **SOLID:**
  - Un widget reutilizable = una sola responsabilidad de presentación.
  - Componentes extendibles por props, no por duplicación por pantalla.
  - Dependencias de UI inyectadas vía constructor; no acoplar widgets a providers específicos de feature.
  - Evitar "God widgets" por pantalla que mezclen layout + lógica + estado.
- **Bajo acoplamiento:** `core/ui/widgets/` no debe importar features; las pantallas de feature sí pueden importar `core/ui`.
- **Alta cohesión:** cada widget en `core/ui` es cohesivo con su responsabilidad visual.
- **Evolución incremental:** el set de componentes mínimo de esta fase debe ser suficiente para las pantallas objetivo; se expande en fases posteriores del producto.
- **No sobreingeniería:** no crear abstracciones nuevas donde alcance refinar las existentes. Si `app_card.dart` ya existe, consolidar; no crear segunda variante.

### FASE 2 — Implementación

**Meta:** cero overflows en pantallas objetivo, navegación back correcta, safe area respetada, set mínimo de componentes UI consolidado.

#### 2.1 Fix navegación back (go_router)

**Problema:** `context.go('/ruta')` reemplaza el stack completo de navegación. En pantallas de detalle o sub-pantalla, el botón back del sistema no tiene historial al que volver, cerrando la app.

**Reglas de decisión:**

| Caso de uso | Método correcto |
|---|---|
| Navegar a pantalla raíz desde bottom nav | `context.go('/ruta-raiz')` |
| Post-login redirect (limpiar historial) | `context.go('/home')` |
| Abrir detalle desde listado | `context.push('/detalle/id')` |
| Ir a sub-pantalla que debe tener back | `context.push('/sub-pantalla')` |
| Reemplazar pantalla actual sin poder volver | `context.pushReplacement('/pantalla')` |

**Archivos a modificar:** `lib/app/router.dart` + calls en pantallas donde se emita navigation desde widgets.

**DoD 2.1:**
- [ ] Auditoría completa de `router.dart` con `go()` vs `push()` correctos por ruta.
- [ ] En todas las pantallas no-root, el back del sistema retorna a la pantalla anterior.
- [ ] En pantalla root (dashboard/home), el back puede salir de la app (comportamiento estándar).
- [ ] `flutter analyze` pasa sin nuevos errores.

#### 2.2 SafeArea y FAB

**Problema:** FAB y elementos de acción cortados por notch/gestos/barra del sistema.

**Reglas:**
- Todo `Scaffold` en pantallas con `floatingActionButton` debe tener `resizeToAvoidBottomInset: true` (default) y el FAB debe estar dentro del árbol de `Scaffold`, no en `Stack` posicionado manualmente a menos que sea deliberado y contemple `MediaQuery.of(context).padding.bottom`.
- Verificar que no haya padding hardcodeado que ignore safe area.
- Usar `SafeArea` en pantallas donde el contenido en pantalla completa (login, splash) puede quedar bajo el notch.

**Pantallas a verificar:** todas las pantallas objetivo + cualquier que tenga FAB.

**DoD 2.2:**
- [ ] FAB visible y accesible en dispositivos con notch y gesture bar.
- [ ] Contenido no queda bajo el notch en ninguna pantalla objetivo.
- [ ] No hay padding bottom hardcodeado que ignore safe area.

#### 2.3 Cero overflows en pantallas objetivo

**Pantallas y problemas específicos:**

| Pantalla | Problema | Fix |
|---|---|---|
| `login_screen.dart` | Layout alto, posible overflow vertical en keyboards/pantallas pequeñas | Wrappear en `SingleChildScrollView`; layout compacto; `KeyboardDismissOnTap` o `GestureDetector` |
| `parameters_screen.dart` | Texto/valor que causa overflow horizontal | `Flexible`/`Expanded` en filas; `TextOverflow.ellipsis` o wrap donde corresponda |
| `audit_list_screen.dart` | Textos largos en items de lista | Limitar filas con `maxLines` + `overflow: TextOverflow.ellipsis`; separar columnas con `Flexible` |
| `users_list_screen.dart` | Overflow en cards de usuarios, buscador | Usar `AppCard` canónico; `AppSearchBar` canónico |
| `user_detail_screen.dart` | Roles como texto crudo/objetos; overflow en nombre/email | Renderizar roles como `Wrap` de `StatusChip`/`Chip`; nombre con `maxLines: 2` |
| `products_list_screen.dart` | Empty state inconsistente | Usar `EmptyState` canónico de `core/ui/widgets/` |
| `dashboard_screen.dart` | Jerarquía visual pobre, placeholder "se ve mal" | Revisar estructura de columnas/filas; `AppCard` con datos; tipografía por niveles del theme |

**Reglas generales anti-overflow:**
- No usar `Row` sin `Flexible`/`Expanded` en hijos con texto variable.
- No usar `Column` sin `Flexible`/`Expanded` o `SingleChildScrollView` si el contenido puede crecer.
- No usar `SizedBox` con altura fija para contenedores de texto variable.
- Todo texto que venga del backend debe tener `maxLines` + `overflow` definidos.

**DoD 2.3:**
- [ ] Cero `RenderFlex overflow` en consola en pantallas objetivo bajo casos de uso normales.
- [ ] Textos largos (nombres, roles, descripciones) se truncan o wrappean de forma controlada.
